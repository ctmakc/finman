# Finman: сквозное шифрование данных пользователя (Finman Vault)

Статус: реализовано 21.11.2026 (v1). Ветка `feat/e2e-vault-1121`, worktree `/fast/finman-wt/e2e`.
Задача владельца: «шифрование там должно быть, чтобы мы даже теоретически к юзердата не могли получать доступ».

## 1. Цель и граница

Финансовые данные пользователя (счета, транзакции, категории, бюджеты, цели, долги, подписки, инвестиции, выписки и импорт, чеки, заметки и описания, отчёты, сплиты, правила, ИИ-переписка, ключи ИИ пользователя) хранятся на сервере только шифротекстом. Ключ есть только у пользователя. Владелец Finman, админ, процесс сервера, база и бэкапы держат байты, которые без ключа пользователя прочитать нельзя.

Сервер видит (и это честно написано на странице Security):
- e-mail, имя профиля, способ входа (пароль / Google / Apple), часовой пояс, тариф и данные оплаты Stripe;
- размер зашифрованного сейфа, номер его версии и время последней синхронизации;
- IP и технические логи запросов (без тела запроса), события аналитики без сумм и текстов (вход, регистрация, «синхронизирован сейф»);
- выставленные счета-инвойсы клиентам (раздел «Счета»): их получатель открывает по ссылке, поэтому сервер собирает PDF (см. §7);
- то, на что пользователь явно дал согласие (MCP-доступ для ИИ-чата, §6.3).

Сервер не видит: пароль (после перехода на схему fm1), ключ сейфа, ключ восстановления, суммы, описания, названия счетов, файлы выписок, ключи ИИ пользователя, переписку с ИИ.

Исключение по согласию на каждый файл: PDF или фото выписки, которое человек сам отдаёт «Finman AI» (кнопка Read statement под текстом, куда уходит файл), один раз проходит через сервер и Google Gemini (`POST /api/statements/read`, consent=1). Сервер ничего из файла не сохраняет; в журнал идёт только событие `statement_read` (режим, страниц, статус проверки) для дневного лимита. Строки и проверка баланса сохраняются уже в сейфе (`POST /api/statements/from-reading` обслуживает движок в браузере).

## 2. Модель угроз

| Угроза | Защищено? | Чем |
|---|---|---|
| Утечка базы или бэкапа | да | в базе только шифротекст AES-256-GCM, ключа там нет |
| Любопытный админ / владелец читает базу | да | то же; пароль на сервер не приходит |
| Взлом сервера с чтением диска | да | ключей на диске нет |
| Взлом сервера с подменой JS приложения | нет (общее ограничение веб-шифрования) | подменённый код может украсть ключ при следующем входе. Снижаем: CSP, SRI на vendor-файлах, хеши сборки в репо, открытый код, нативные приложения со своей сборкой |
| Перехват трафика | да | TLS + в теле только шифротекст |
| Подбор пароля по украденной базе | затруднён | Argon2id (64 МиБ, 3 прохода) на клиенте, на сервере bcrypt от производного токена |
| Пользователь забыл пароль | данные спасает только ключ восстановления | показываем один раз, просим сохранить |
| Активный MCP-доступ ИИ-чата | по согласию | сервер расшифровывает в памяти только во время вызова инструмента ИИ; отзыв доступа стирает обёртку ключа |

## 3. Ключи

```
пароль ──Argon2id(salt_user, m=64MiB, t=3, p=1)──► masterKey (32 байта, только в браузере)
masterKey ──HKDF-SHA256 "finman/auth/v1"──► authToken (hex) ──► уходит на сервер ВМЕСТО пароля, там bcrypt(authToken)
masterKey ──HKDF-SHA256 "finman/kek/v1"───► KEK_pw (AES-256-GCM)
случайный vaultKey (32 байта, AES-256-GCM)  ── шифрует сейф
wrapped_pw = AES-GCM(KEK_pw, vaultKey)          ── хранится на сервере
recoveryKey (32 случайных байта, показ один раз, вид FM1-XXXX-…)
recoveryKey ──HKDF "finman/recovery/v1"──► KEK_rc;  wrapped_rc = AES-GCM(KEK_rc, vaultKey) ── на сервере
```

- `salt_user` — 16 случайных байт на пользователя, хранится открыто (`users.kdf_salt`), отдаётся `POST /api/auth/prelogin`.
- Вход через Google/Apple: пароля нет, при первом открытии сейфа пользователь задаёт «пароль сейфа» (та же схема, authToken не нужен). `users.kdf` у таких аккаунтов остаётся `legacy`: это поле описывает, как отправляется ПАРОЛЬ ВХОДА, а к Google-аккаунту может быть привязан пароль (без этого он переставал бы входить). Соль/параметры сейфа лежат в `kdf_salt`/`kdf_params`.
- Смена пароля: браузер открывает сейф старым паролем, перешифровывает только `wrapped_pw` новым KEK и шлёт новый authToken. Данные не перешифровываются.
- Новый ключ восстановления: браузер делает новый `wrapped_rc`, старый перестаёт работать.
- Забытый пароль: вход по ключу восстановления → новый пароль → новый `wrapped_pw`. Без ключа восстановления данные потеряны, сервер помочь не может (честно предупреждаем при выдаче ключа).
- Шифрование: WebCrypto AES-256-GCM, IV 12 случайных байт на каждую запись, AAD = `finman-vault:v1:<userId>`.

## 4. Хранилище

Сейф = SQLite-база пользователя целиком (та же схема, что на сервере, только его строки), сжатая gzip и зашифрованная `vaultKey`.

- Сервер: таблица `user_vaults(user_id, version, blob, size, wrapped_pw, wrapped_rc, updated_at)`; столбцы `users.kdf`, `users.kdf_salt`, `users.kdf_params`, `users.vault_state` (`none` | `active`).
- Браузер: sql.js (SQLite в WebAssembly). Логика приложения (маршруты `/api/accounts`, `/api/transactions`, отчёты, бюджеты, прогноз…) собрана в «движок» `public/js/vault/engine.js` из тех же файлов `routes/`, `models/`, `services/`, что и сервер, и работает над расшифрованной базой в памяти вкладки. Экраны приложения не меняются: `fetch('/api/…')` перехватывается и уходит в движок.
- Синхронизация: после каждой записи браузер через 1,5 с шифрует базу и шлёт `PUT /api/vault/blob` с `If-Match: <version>`. Конфликт (другое устройство успело раньше) → 409 → браузер скачивает новую версию, повторяет свои несохранённые запросы поверх неё и шлёт снова.
- В открытом виде данные живут только в памяти вкладки; в localStorage/IndexedDB открытый текст не пишется. Закрыли вкладку или вышли — нужно снова открыть сейф (при входе паролем это происходит само).

## 5. Миграция существующих пользователей

1. Пользователь входит как обычно (старый протокол, пароль ещё приходит на сервер последний раз).
2. Браузер видит `vault_state=none`, показывает экран «Шифруем ваши данные»:
   - `GET /api/vault/legacy-export` — его открытые строки по всем таблицам сейфа;
   - строит локальную базу, считает строки по таблицам;
   - создаёт vaultKey, ключ восстановления, обёртки, authToken;
   - `POST /api/vault/setup` — шифротекст, обёртки, соль, authToken (сервер меняет хеш пароля на bcrypt(authToken));
   - показывает ключ восстановления, пользователь подтверждает «сохранил»;
   - `POST /api/vault/purge-legacy` с числом строк по таблицам; сервер сверяет со своими счётчиками и только при полном совпадении удаляет открытые строки этого пользователя в одной транзакции; `vault_state=active`.
3. Новые пользователи получают сейф сразу при регистрации.
4. Сбой посередине безопасен: открытые строки стираются только после успешной загрузки сейфа и совпадения счётчиков; повторный вход повторяет шаги.

### Бэкапы с открытыми данными

Бэкапы `/opt/finman-backups/*` и `finman_finman-data/_data/backups/*` до перехода содержат открытые данные. План:
- до выкатки — свежий бэкап (обязателен для отката);
- через 14 дней после выкатки, когда все активные пользователи перешли: удалить бэкапы старше даты выкатки, кроме одного «аварийного», зашифрованного `age` ключом владельца офлайн; через 30 дней удалить и его;
- новые ночные бэкапы содержат только шифротекст сейфов;
- SQLite после удаления строк: `VACUUM` чтобы открытые страницы не остались в файле, WAL — checkpoint(TRUNCATE).

### 6.3 MCP-доступ для ИИ-чата по явному согласию

ChatGPT и Claude подключают Finman как удалённый MCP-сервер, и вызывать инструменты может только сервер. Поэтому:
- при нажатии «Разрешить» на странице OAuth браузер (сейф открыт) генерирует `grantSecret`, заворачивает им vaultKey и отдаёт серверу обёртку и секрет; сервер хранит только обёртку и хеш токена, сам `grantSecret` живёт только внутри выданного ИИ-приложению токена;
- при каждом вызове инструмента сервер разворачивает ключ из токена, расшифровывает сейф в памяти, выполняет инструмент тем же движком, при записи шифрует и сохраняет новую версию, всё стирает из памяти;
- экран согласия прямо говорит: «пока подключение активно, сервер Finman расшифровывает ваши данные в момент запроса вашего ИИ»; отключение в настройках удаляет обёртку, после этого прочитать нельзя;
- альтернатива без доверия серверу: локальный MCP (Claude Desktop, Claude Code, Cursor) — `npx` пакет, который открывает сейф ключом на компьютере пользователя (этап 2).

## 7. Что невозможно без чтения данных (перечень для пользователя, только по явному согласию)

1. Вызовы инструментов MCP из удалённого ИИ-чата (§6.3).
2. Цифры в письмах и push-уведомлениях (по умолчанию без цифр; этап 2 — согласие «присылать суммы в письмах»).
3. Автосинхронизация банков через API (банк отдаёт данные серверу).
4. Публичная ссылка на инвойс для клиента (PDF собирает сервер).
5. Помощь поддержки «посмотрите мои данные» — только если пользователь сам выгрузит файл.
6. Чтение PDF или фото выписки ИИ Finman (сервер + Google Gemini, без хранения) — согласие на каждый файл в мастере импорта. CSV, OFX и QFX читаются в браузере без ИИ.

## 8. Протокол API

- `POST /api/auth/prelogin {email}` → `{kdf: "legacy"|"fm1", salt, params}` (для несуществующих e-mail — детерминированная фальшивая соль).
- Вход/регистрация/смена пароля/удаление аккаунта/вход на странице OAuth: при `kdf=fm1` в поле `password` уходит authToken.
- `GET /api/vault/meta`, `GET /api/vault/blob`, `PUT /api/vault/blob` (If-Match, 409 VERSION_CONFLICT, тело обязано начинаться с `FMV1`), `POST /api/vault/setup`, `GET /api/vault/legacy-export`, `POST /api/vault/purge-legacy` (пересчёт внутри транзакции, secure_delete, затем WAL checkpoint и VACUUM), `POST /api/vault/rewrap`.
- `/api/v1/*` (персональные токены) для сейфа → 409 `VAULT_ENCRYPTED`; MCP через PAT отвечает «подключите заново через Allow».
- CSP: `script-src` + `'wasm-unsafe-eval'` (Argon2 и SQLite в WebAssembly), `connect-src 'self' https:` (свой ИИ пользователя: OpenAI, Anthropic, Gemini, OpenRouter, DeepSeek, Mistral, Groq, xAI, свой адрес).
- MCP: `vault_grants(token_hash, user_id, wrapped_vk, created_at, revoked_at)`.

## 9. Проверка

- Юнит: криптография (обёртка/разворот, неверный пароль, ключ восстановления), сейф (версии, 409, purge только при совпадении счётчиков), движок (счёт, транзакция, баланс, отчёт в sql.js).
- Стейджинг finman.apps.mmix.biz: сценарий браузера — регистрация, сейф, добавить транзакцию, выход, вход, данные на месте; SELECT по таблицам — пусто, в user_vaults шифротекст.
- Копия прод-базы: миграция всех пользователей скриптом-эмулятором браузера, счётчики строк до/после по каждому пользователю.
- Прод: бэкап → выкатка → тестовый пользователь → SELECT показывает шифротекст → вход в браузере показывает данные.
